# 可可助手 EXE 与微信小程序架构评估

## 目标
在不先实现或配置云服务的前提下，基于已确认的产品边界，梳理可维护的 Windows EXE、私有管理端同步、公共资料发布与微信小程序方案，并明确依赖、成本和待确认风险。

## 当前状态
- 阶段：7 — Windows 独立用户与管理软件
- 下一步：用户体验桌面预览版；在线资料更新端点与小程序按原路线后续实施。
- 范围：实现并本机打包桌面版；不创建云资源、不提交或推送 GitHub。

## 已确认边界
- 普通用户只能使用用户端，管理端不进入 EXE 或小程序。
- 管理端暂时在各台电脑本地运行，通过私有 GitHub 仓库拉取/提交同步，不做网页登录后台。
- 对外发布的只有公共图鉴与攻略；私有仓库是管理源，不直接给用户端凭据。
- EXE 断网时使用最近一次成功获取的公共资料缓存；联网后再检查更新。
- 暂不做玩家个人数据/账号同步；未来官方游戏 API 逐次读取，驱动快能力先限 Windows EXE。
- 接受公共资料使用静态 HTTPS 发布；托管商与小程序可用性尚未决定。
- 先避免自建/付费后台；后续再讨论费用与托管服务。

## 关键问题
1. 独立公开资料发布目标能否满足微信小程序网络与备案要求？
2. 管理端如何通过私有 GitHub 在多台电脑安全同步，避免令牌进入前端/EXE？
3. 当前用户端与管理端代码/存储边界是否足以拆分打包？
4. EXE 程序更新与资料更新是否应分开？

## 已做决策
| 决策 | 理由 |
|------|------|
| 本轮只研究与规划，不改应用或配置云服务 | 先确认架构，避免返工和费用 |
| 私有 GitHub 是管理源；公共资料需要独立发布 | 普通用户不能安全读取私有仓库 |
| 使用独立计划目录 | 本议题与既有 UI 改造任务不同 |
| 管理工具与用户客户端从同一私有源代码库构建为不同发行目标 | 用户发行物不能包含管理入口/管理模块；管理侧需要本地文件写入和Git同步能力 |
| 先补管理端数据写回与跨电脑Git同步，再包装用户EXE；小程序后置 | 当前管理保存依赖浏览器存储，尚未形成可复现的仓库数据更新链路 |
| 资料更新和程序更新分开 | 资料可频繁更新，程序发行需安装/审核节奏；缓存应支持离线与失败回滚 |
| 当前首个实施阶段只打通管理端本地写回和 Git 同步，不做 EXE 打包/云端发布 | 遵循用户确认的顺序，减少同时变更多个边界的风险 |

## 推荐路线摘要
1. 建立私有管理目标：管理编辑真正写入仓库里的结构化数据；同步使用本机 Git/Git Credential Manager 等安全授权，不在网页、EXE或小程序内嵌 PAT；冲突前先备份并展示差异。
2. 建立明确的用户发行目标：仅打包用户导航、公共图鉴/攻略和必要用户功能；CI/烟测确认发行目录不含管理入口、管理脚本、原始维护快照或凭据。
3. Windows EXE先内置一份完整资料并保证离线可用；在线资料更新采用版本清单、文件哈希、临时下载、校验后原子切换、保留上一份可回滚快照。程序更新与资料更新分开；首个版本先手动安装更新。
4. 小程序作为独立适配客户端，复用规范化资料格式和无界面业务逻辑，不复用桌面 DOM；上线前用官方文档与开发者工具核验网络域名/备案、体积、隐私、审核和主体要求。
5. 若小程序网络条件可满足，再评估只发布可公开数据的独立静态仓库/托管目标；绝不把私有管理仓库或其令牌暴露给用户。若没有合规的数据端点，则资料随客户端版本发布。
