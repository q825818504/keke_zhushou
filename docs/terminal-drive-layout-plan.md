# 终端驱动摆放与智能匹配计划

更新日期：2026-10-07

状态：基础摆放、套装约束与求解器已完成；真实用户仓库接入待开发。
维护基线：`main` 分支；实现与数据随项目 GitHub 仓库同步。

## 目标

为角色提供可编辑、可解释的终端驱动摆法。攻略默认摆法必须先满足角色所选空幕的完整四件套形状要求，再尽量铺满终端并满足角色终端被动；后续使用玩家实际仓库中的驱动实例、角色属性权重和多角色占用关系，推荐可实际装备的方案。

## 已完成的能力

- 终端槽位以固定网格记录，驱动形状使用稳定的图鉴 `shape_id`，包含型号、形状和朝向；相同型号的横向与纵向驱动不能互换。
- 12 套空幕的必需形状与来源截图分层保存。套装形状为硬约束：必须具备四种要求形状，重复同形状不能补齐缺失形状。
- 求解优先级为：满足所选套装形状 → 最大化已填槽位 → 最大化角色偏好型号数量 → 按实际驱动属性评分。套装约束不可由分数、库存或预算放宽。
- 同一个终端可返回多个不同形状数量组合；形状组合和坐标摆法分别枚举。管理端保留自由编辑、撤销、补满、重排和保存。
- 纯计算模块 `drive_layout_solver.js` 可在浏览器和 Node 复用，接受形状库存、实例 UID、固定/排除 UID、属性权重或自定义评分，并显式标明无解、结果截断和搜索预算耗尽。
- 全部 25 名角色的终端文案与攻略站逐条核对。24 名有资料角色目前一致；塔吉多双方都没有终端条目。真红修正已进入来源角色文件和维护覆盖层。

## 现有模块边界

- `drive_layout_solver.js`：纯约束搜索、候选组合、库存实例选择和排序，不依赖界面。
- `terminal_puzzle.js`：将角色、终端与所选空幕转成套装约束，并汇总摆放状态。
- `terminal_editor.js`：管理端的格子绘制、驱动选择、拖放、撤销和保存交互。
- `data/knowledge/encyclopedia/cassette_set_requirements.json`：维护者核对后的套装形状要求；`import_mysqil_cassettes.py` 重导入时保留该补充层。
- `character_overrides.json`：角色可维护的终端摆法和终端来源修正；公共用户包只包含展示/求解必需的资料，不包含管理编辑器和维护截图。

## 下一阶段：玩家仓库驱动的方案匹配

### 16.1 定义库存快照契约

建立独立于界面的库存 schema。每个驱动实例至少需要稳定 UID、型号、固定朝向 `shape_id`、主副属性及数值、锁定状态、当前装备角色；快照带格式版本和生成/导入时间。属性名和百分比单位在进入求解器前统一。先确定可验证的手工录入或文件导入流程；只有确认游戏客户端可合法、可靠地提供数据后，再增加自动读取适配器。

### 16.2 把候选排序变成角色可配置策略

复用角色词条权重，提供主属性、副属性、套装偏好及可选评分回调。硬约束始终优先：必需套装形状必须完整；然后在可行范围内比较填充格数、角色终端型号加成、实际装备属性权重。权重配置要版本化，并在结果中列出每个候选的评分拆解，不能把线性权重冒充完整伤害模拟。

### 16.3 处理 UID 唯一性与多角色冲突

单角色方案中的驱动 UID 不可重复使用。队伍匹配需要跨角色协调共享库存：先生成每名角色的前 N 个候选，再做有界组合搜索；返回明确的搜索范围、最优性/截断状态和无法分配原因。逐角色贪心结果不能标成全队最优。

### 16.4 接入用户工作流

稳定 schema 与排序契约后，再设计库存录入/导入、筛选与角色权重界面。结果需说明：满足的四件套形状、终端被动次数、实际使用的每件驱动 UID 与属性贡献、未采用驱动的原因。库存或权重更新后，结果绑定的快照版本必须仍有效才允许保存。

## 验收条件

- 缺少任一必需形状时返回无可行解，绝不降级成“已激活”。
- 形状数量不足、重复 UID、固定/排除实例冲突均给出确定结果和原因。
- 对相同库存快照和权重版本重复计算得到相同候选顺序。
- 不同横/竖或 L 朝向的库存差异会影响候选，不会被相同型号混淆。
- 多角色结果确保 UID 唯一，并明确 `searchComplete`、预算、截断和最优范围。
- 用户端只读方案和资料；维护编辑、私有来源快照及 Git 凭据不进入用户发行物。
- 现有终端、空幕、来源导入、保存与发行隔离回归持续通过。
