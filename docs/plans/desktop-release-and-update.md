## 仓库职责与发布白名单

### GitHub

维护源码、原始和维护后的知识配置、公共配置导出器、安装脚本、更新器实现、测试、发行版本记录。管理端保存先写工作副本，发布时同步 GitHub，并生成可分发数据。

### Gitee

建议采用独立 `main` 发布分支；当前仓库没有 refs，尚无已确定的默认分支。发布结构：

```text
channels/
  app-latest.json             # 程序最新版的签名清单
  config-latest.json          # 公共配置最新版的签名清单
metadata/
  app/v1.0.json               # 不可变版本记录
  config/r1.json
README.md                    # 用户下载/安装说明
licenses/                    # 随分发必须保留的许可通知
```

安装器、程序更新包、配置包及图片包放发行附件或已验证的制品存储；Git只维护小型索引和必要公共JSON。使用全新产物暂存目录和文件白名单发布，不能用GitHub仓库镜像、全量文件复制或源码目录作为Gitee的发布输入。

Gitee不放 `.py`、管理端脚本、开发项目、测试、`.git`、IDE文件、玩家账号/背包/截图、签名私钥或访问令牌。运行所需前端代码作为构建后的程序资源随二进制发行，不作为可更新配置上传；公共配置包只接受JSON和许可图片，不接受JS、Python、DLL等可执行内容。

Gitee发布库应提供匿名读取；写入权限只由维护端持有。程序收到登录HTML、验证码、错误网页或不完整JSON时视为版本检查失败，不能把它当作“无更新”。

## 安装形式及Gitee配额

本次已核实Gitee官方社区版限制：Git单文件50MB、单仓库500MB；附件单文件100MB、单仓库附件总容量1GB。

来源：https://help.gitee.com/questions/Gitee%E4%BA%A7%E5%93%81%E9%85%8D%E9%A2%9D%E8%AF%B4%E6%98%8E

当前最终EXE为172694591字节，约165MiB。不能假定换成安装包后会小于100MB。设计两种输出：

- 本地完整离线安装包：方便直接传给用户或使用能够容纳它的下载渠道。安装后所有必需文件和默认配置已经就绪；用户端启动仍需成功检查远端程序版本。
- Gitee联网安装器：用户只打开一个小型安装器，由它获取版本清单、自动下载分块、拼合校验并安装完整程序。更新包分块建议最多90MiB，低于100MB附件上限。用户不需要手动合并文件。

如果要求Gitee里也只有一份完整离线安装附件，必须先实际压缩测量；超过100MB时需要扩大可用制品存储，不能宣称当前免费附件方案满足此要求。Inno Setup支持磁盘分卷，可用于完整离线包的分卷输出，但分卷安装材料和单个离线EXE是两种交付形式。

Inno Setup文档：https://jrsoftware.org/ishelp/topic_setup_diskslicesize.htm

首版默认按当前Windows用户安装到 `%LOCALAPPDATA%/Programs/KekeAssistant`，建立快捷方式和卸载项，减少普通升级的权限要求。选择全用户安装时再明确申请管理员权限。WebView2检测/安装流程在安装器实现阶段确定；Python、OCR推理库及原生运行资源随程序发行。游戏插件部署和可选手柄驱动仍保持用户主动操作。

安装数据布局建议：

```text
%LOCALAPPDATA%/Programs/KekeAssistant/
  KekeAssistant.exe           # 入口和更新门禁
  KekeUpdater.exe             # 主程序退出后安装新版本
  active-version.json
  app/v1.0/                  # 编译后的程序、依赖、模型、内置公共配置
  app/v1.1/

%LOCALAPPDATA%/KekeAssistant/
  public-config/             # 已校验的在线配置缓存
  update-cache/              # 下载和事务暂存
  desktop-user/              # 用户偏好
  player-inventory/          # 已有原生快照
  vision-scans/              # 已有OCR批次与截图
```

程序版本目录与用户资料分离；升级和卸载默认保留已有个人资料。新程序在独立版本目录准备好后切换当前指针，不在运行进程使用的目录里逐文件覆盖。

## 版本规则

- 首个正式发行版本v1.0，内部对应1.0.0；用户显示v1.0。
- 下次正式发行自动计算v1.1，然后v1.2；v1.9之后是v1.10，不能用小数/浮点比较版本。
- 版本记录只有一个权威入口，例如GitHub维护的 `release-state.json`；界面、安装器、清单和程序读取同一值。
- “生成正式发行安装包”使用下一个候选版本。只有构建、产物上传、匿名下载核验和最新版清单切换全部成功后，才记录为已发布。失败重试同一候选版本，日常测试构建不自动增加正式版本。
- 多维护者发布时重新读取远端最后发行号，并使用并发锁/预期提交校验，防止覆盖其他维护者刚发布的版本。
- 只发布配置不增加应用版本，配置使用r1、r2等独立递增修订；相同导出内容按哈希判断无变化，不重复创建修订。
- 如配置需要新程序才支持，清单声明兼容版本/格式版本；先发布支持它的程序。配置更新失败时，新安装包附带的兼容配置可使用。

## 启动状态与强制更新

程序打开后先展示清晰的更新页面，只提供进度、重试和退出，不提前显示主功能。

1. 在线获取 `app-latest.json`。设置有限连接/读取超时和重试；每次启动重新向远端验证，可用HTTP条件请求确认最新状态，不能断网后直接采用缓存版本结论。
2. 检查签名、产品/平台身份、清单格式和版本号。失败、空文件、无法解析、无法下载或身份不符，停留在门禁页。
3. 本机版本低于远端最新版时，强制下载更新。更新未安装成功前不能进入旧主界面；用户可以退出，不能跳过。
4. 校验每个分块以及合并包的大小/哈希。更新器等待运行进程退出，解压到独立目录，完成布局校验后切换版本并重新启动。下载中断、磁盘不足或文件占用不改变当前指针；可重试。
5. 本机版本等于远端正式版本，程序版本门禁通过。本机版本高于远端时需明确受签名清单授权，例如受支持版本范围；普通发行端不能直接忽略版本不一致。生产发布采用单一最新版要求，避免失败发布/回滚导致版本判断含糊。
6. 在线获取 `config-latest.json`。发现新修订时自动下载数据和图片，校验格式、路径、哈希、签名及程序兼容性，整批切换配置指针。
7. 配置检查或下载失败时，使用上次完整且兼容的缓存；没有缓存则用安装包附带配置。显示“本次配置更新失败，正在使用本地配置”，允许进入主界面。
8. 载入公共配置，随后打开配队、角色、背包和读取数据等主功能。没有任何完整兼容配置的异常安装需要修复，不能使用半个配置包。

“每次启动更新配置”表示每次启动都向远端检查并保证选择最新版；已经确认相同修订/哈希时无需重新下载所有图片。

强制版本检查必须由实际主入口执行；不能只放在桌面快捷方式里。直接打开应用本体也要经过检查。启动器已经检查过时可通过一次启动会话交接结果，避免同一次用户启动重复检查。生产版本不提供跳过版本检查的测试开关。

| 场景 | 是否进入主界面 |
| --- | --- |
| 程序版本无法获取、超时、错误页或签名失败 | 否，重试/退出 |
| 有程序新版，用户未安装或安装失败 | 否，更新/重试/退出 |
| 程序版本通过，最新配置下载成功 | 是，使用最新配置 |
| 程序版本通过，配置服务失败 | 是，使用完整本地配置并提示 |
| 配置下载一半、校验失败或格式不兼容 | 是，继续使用完整缓存或内置配置 |

联网检查不是后台持续轮询，不在用户使用过程中反复触发强制重启。

## 更新清单和信任

程序发布清单包含产品ID、平台、最新版、发行序号、发布日期、说明、分块URL/大小/SHA256、合并包SHA256、兼容资料格式。配置清单包含修订号、格式版本、适用程序版本、JSON/图片包位置和哈希。

清单采用带签名的单文件信封，下载字节直接验证签名后再解释内容，避免“清单文件和签名文件更新时刻不同”。维护端保存签名私钥，客户端内置可信公钥；SHA256用于检查传输内容，签名确认发行来源。版本序号和本机已确认发行记录用于发现未授权降级。

更新包解压只允许预期相对路径；阻止绝对路径、`..`、链接跳出、未知可执行配置和越界大小。配置在后台完整校验后再生效，失败保留旧完整版本。配置不覆盖用户的背包、扫描截图、持有角色及个人偏好。

配置导出以现有已整理的知识JSON为来源，生成公共字段白名单和图片列表；现有团队维护覆盖要合并到有效配置中。用户端通过固定字段映射加载JSON，不能把Gitee下载的JS当数据执行，也不能把GitHub的整个资料目录原样发布。

## 管理端远程发布流程

“保存”保持为本地维护操作；新增“发布配置”，让本地草稿和线上发行有清楚边界。

1. 保存并校验当前维护内容，核对有效配置和引用图片齐全。
2. 将维护配置同步GitHub，记录对应源码/数据提交。
3. 从白名单导出JSON/图片包，生成修订、哈希和签名，展示本次发布摘要。
4. 上传不可变产物到Gitee发行附件/制品存储，读取并校验上传结果。
5. 用不登录的下载请求校验将被用户使用的全部URL，确认不是登录页/验证码/权限错误。
6. 最后更新签名的 `config-latest.json`；确认完成后报告发布成功。

“发行程序”先完成用户目录构建和安装器生成，使用相同的产物上传/匿名核验/最后切换清单规则。程序全部上传且可用之前不能推进 `app-latest.json`，避免所有旧客户端被强制要求下载一个尚不存在的版本。

Gitee写入权限只保存在维护电脑的系统凭据库；本机签名私钥不进入任一仓库。用户安装包不包含写入令牌。普通数据/配置发布只导出公共内容。

Gitee附件总容量有限，发布前必须计算本次所需配额，满额则停止发布并保持旧清单有效。保留版本数量和过期附件清理需要明确策略；首版不自动删除既有线上发行。配置/图片按内容复用以减少重复上传。

## 实施顺序和验收

### 1. 版本与配置导出

新增统一发行版本记录、公共配置JSON导出器及格式说明；从当前0.1预览编号迁移到正式v1.0。准备可复现的配置包、图片清单、版本比较及兼容加载。

验收：当前角色、推荐、词条、终端、阵容、图片使用导出JSON加载与现有展示一致；导出不包含源码、个人数据和本机凭据。

### 2. 安装布局与更新器

用户端改安装目录构建；管理端继续单EXE。生成离线安装器以及Gitee适用的联网安装入口/分块产物。支持安装、快捷方式、更新事务和卸载。

验收：另一台干净Windows电脑无需Python/Node即可安装运行；程序资源和内置配置完整；游戏插件仍由用户明确部署；升级保留已有用户设置、背包和OCR截图。

### 3. Gitee发布工具和管理入口

实现独立发布白名单、签名、凭据存储、配置发布按钮和程序发行流水线；主仓库默认origin继续指向GitHub，Gitee不成为源码镜像远端。

验收：匿名检查真实清单和每个附件URL；Gitee中不存在源码树、管理工具、玩家数据；部分上传失败不会更新latest或消耗正式版本号。

### 4. 用户启动更新门禁

实现程序强制更新、配置自动拉取和离线回退、可理解的更新进度/失败提示；保留用户偏好，避免其他运行实例正在扫描时覆盖文件。

验收：断网或版本清单错误禁止进入；配置下载失败可以使用本地数据；新版安装失败可重试；直接运行本体不可绕过；同一次启动只发起一次程序版本检查。

### 5. 两台电脑真实发行验收

发布首版v1.0，在第二台电脑安装；管理端改一项推荐并单独发布r2，重开用户端获取r2；发行v1.1，重开v1.0必须先完成程序更新。分别测试程序网络失败和仅配置失败，确认两种规则不同。
